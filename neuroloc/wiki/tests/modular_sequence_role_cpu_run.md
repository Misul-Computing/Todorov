## Frozen common architecture

Both rungs use the same host geometry and deployed feature operation:

- Residual width `64`.
- Eight zero-indexed host blocks.
- Four heads for every sequence mixer.
- Recurrent head width `16`.
- Recurrent chunk length `32`.
- Zero dropout.
- Untied input embedding and output projection matrices.
- Transformerov source-native initialization.
- Transformerov's bias-free, four-times-width, two-branch gated feature block
  in every host block.
- Transformerov's source block `n1` and `n2` RMS normalizations, recurrent
  per-head `onorm`, and final `nf` RMS normalization, with source dimensions,
  learnable scales, and resolved epsilon behavior unchanged.
- Transformerov recurrent `bp`, `ag`, and `og` projection biases retained
  exactly.
- Bias-free public routed `qkv` and output projections and a bias-free final
  output head.
- No reciprocal feature mixer.
- No `nextlat` module, objective, optimizer entry, or ledger entry.

The sequence schedule is fixed:

- Blocks `0` and `4` use the public routed selected-set mixer.
- Blocks `1`, `2`, `3`, `5`, `6`, and `7` use the frozen Transformerov recurrent
  mixer.
- Block `0` is local-only.
- Block `4` has a two-remote-block budget in the routed rung.

For block input `x`, the host alone applies:

`u = x + sequence_mixer(sequence_norm(x))`

`next = u + feature_mixer(feature_norm(u))`

Every sequence mixer accepts one finite `[batch, time, width]` float32 tensor
and returns one same-shape float32 delta on the same device. The host owns both
normalizations and residual additions. The public Monodratic block wrapper and
its feature mixer must not enter the graph.

The recurrent mixer begins with zero state per layer, batch, and forward. State
is sequence-internal, crosses only permitted positions and chunks, is never
returned, cached between calls, serialized, or shared between layers or
examples, and retains the source state-norm clamp unchanged. The routed mixer

## Fatal-bypass firewall

The original task geometry permits a recurrent path to absorb early rule
tokens and carry the answer mapping directly to the query, which would make a
successful answer uninterpretable. Every rung-one intact, training, baseline,
and intervention arm retains all early recurrent resets below. The carry-reset
and carry-shuffle arms additionally apply only their named intervention at
position `96`. The query-only remote-read rule applies to every selected-set
training and evaluation arm. The dense baseline retains every recurrent reset
but is explicitly exempt from the query-only remote-read rule.

### Early-block recurrent resets

Every recurrent mixer at host blocks `1`, `2`, `3`, `5`, `6`, and `7` resets
its internal state immediately before positions `8`, `16`, `24`, `32`, `40`,
`48`, `56`, `64`, `72`, and `80`. Position `0` begins from zero. The reset before
position `80` prevents any rule-bearing state from entering the cue region.
There are no firewall resets at positions `95`, `96`, or `97`; a state
intervention may add the separately defined reset or shuffle immediately
before position `96`.

These resets are specific to rung one. Rung two must accumulate across its
count region and therefore uses no early-block firewall resets.

### Query-only remote read

Host block `4` runs the public route projection, packed-index construction, and
search normally over the complete sequence. Its raw public route is logged.
The effective remote route is then masked to `-1` at every position except
position `126`. The learned route has a two-slot budget at position `126`, but
either slot may be `-1` when public search underfills. Every valid learned ID
must be unique and in `0..14`. Underfill is recorded and is not itself an abort
or permission to substitute an ID. The internally supplied one-local-block path
remains active at every position. Both raw public and effective masked routes
are asserted in memory. Query-example rows record only position `126`, while
call-summary rows retain the compact raw-and-effective canonical-bypass list
below.

The public search's canonical early bypass when `remote_limit` is no greater
than the configured selected width remains unchanged and is visible in raw-
route telemetry. Each call summary stores one position-ordered entry with
exactly `position`, `remote_limit`, configured-width `raw_remote_ids`, and
configured-width `effective_remote_ids`, both including `-1` sentinel slots,
for every bypass position. Raw IDs are captured before forcing, masking, or
overriding; effective IDs are captured only after the call's effective route
is final. Neither stored list may then be mutated. All batch and route-group
rows at that position must equal the stored pattern. The list is empty when
selected width is zero, covers positions `0..23` at width two, and covers
positions `0..127` at width fifteen. Every stored non-query position has an
all-`-1` effective list. The width-fifteen entry for position `126` is
mandatory and its effective IDs must exactly equal every position-`126`
`query_example` row belonging to that call.
Query-example rows set `canonical_bypass_ids` to `null`; their position-`126`
raw IDs are not relabeled as bypass telemetry. Query-only masking makes early
raw IDs outside position `126` ineffective for attention. At position `126`,
no canonical-ID, repeated-ID, dense, or local fallback may fill an underfull
learned route.

The all-eligible donor and same-checkpoint all-eligible clone expose all 15
remotely causal blocks only at position `126`; their effective remote IDs are
also `-1` elsewhere. The separately trained dense baseline is a named stronger
control: block `0` remains local and block `4` uses full causal attention. It
retains every recurrent firewall reset but is exempt from query-only remote
masking. It is evidence that the host can learn the task with full causal
access, not evidence for selected-set routing.

### Reconstructible routing counters

Every routed call summary carries two compact histograms. The
`block_load_histogram` is ordered by strictly increasing `load` and has one
record with exactly `load` and `bucket_count` for each observed packed-bucket
load, including load zero when any bucket is empty. Zero-frequency records are
forbidden. Across address space `16`, batch size `B`, and sequence block count
`N = time / 8`, it must satisfy
`sum(bucket_count) = B * 16`,
`sum(load * bucket_count) = B * N`,
`max_bucket_load = max(load)`, and
`overflow_count = sum(max(load - 64, 0) * bucket_count)`.

The `valid_posting_histogram` is ordered by strictly increasing
`valid_posting_count` and has one record with exactly
`valid_posting_count` and `search_row_count` for each observed count among
non-bypass batch-position-route-group rows. The detached audit calls the
pinned public `probe_addresses` helper with the exact three-argument ABI above,
then gathers the already built packed postings and applies the public search
validity boundary `0 <= block_id < remote_limit` solely to count valid posting
entries. Route groups are fixed at `1`. For batch size `B` and time `128`, the
derived `search_rows` count is exactly `0` at width zero,
`B * 1 * (128 - 24) = B * 104` at width two, and `0` at width fifteen. The
general nonzero-width formula is
`B * route_groups * (time - canonical_bypass_position_count)`. It must satisfy
`search_rows = sum(search_row_count)`,
`addresses_probed = search_rows * 4`, and both `posting_reads` and
`candidate_blocks` equal
`sum(valid_posting_count * search_row_count)`. The list is empty if and only if
`search_rows` is zero;
otherwise zero-frequency records are forbidden and a zero-valid-posting bin is
included exactly when observed. The histogram and bypass list are evidence
only and cannot alter the raw or effective route. A coherent rescaling of the
histogram frequencies and all dependent counters is rejected because its
frequency sum cannot equal the geometry-derived `search_rows`.

## Canonical serialization and rung-one generator

Every stochastic stream owns one dedicated CPU `torch.Generator`. NumPy,
Python `random`, data-loader RNGs, and a shared generator are forbidden. A
generator call for batch size `B` performs these operations in this exact
order:

1. Draw the complete int64 filler tensor with
   `torch.randint(0, 32, [B, 128], generator=g)`.
2. Visit rows in ascending order `0..B-1`.
3. For each row, draw `torch.randperm(10, generator=g)[:4]` as
   `rule_blocks`.
4. Draw `torch.randperm(16, generator=g)[:4]` as `answer_indices`.
5. Draw one `torch.randint(0, 4, [1], generator=g)` as `condition`.
6. In rule order `r = 0, 1, 2, 3`, assign token
   `64 + 16 * r + answer_indices[r]` at position
   `8 * rule_blocks[r]`.
7. Assign token `32 + condition` at position `80` and token `36` at position
   `126`.

All unassigned positions, including `81..125` and `127`, retain the original
filler draw. The vocabulary is `128`; ten candidate blocks cover `0..79` with
block width `8`; answer tokens are `40..55`; the target is
`40 + answer_indices[condition]`; and the required source is
`rule_blocks[condition]`. Position `96` remains the intervention boundary.

The exact rung-one payload fields are `tokens`, `targets`, `condition`,
`rule_blocks`, `answer_indices`, and `required_source`. Tensors are converted
to nested Python integer lists without dtype annotations. Golden fixtures and
artifact payload hashes use UTF-8 JSON with `sort_keys=True`, separators
`(",", ":")`, `ensure_ascii=True`, and `allow_nan=False`. Seed `123456` with
batch size `2` must hash to
`98ff3b54f14306135eafe5a92da7abdf1111cd8690e511188bb5f0e44dcab2a9`.
Any field, draw-order, dtype, row-order, or hash mismatch blocks training.

Every rung-one training stage requests exactly one batch of `16` per update
and advances its named generator continuously across that stage. Held-out
evaluation constructs all `512` examples in one generator call, persists that
payload, and only then slices it into 16 fixed batches of 32.

## Optimizer and schedule contract

Every stage creates a fresh AdamW optimizer and fresh schedule. Optimizer and
schedule state never transfer between stages. Common settings are:

- Betas `(0.9, 0.95)`.
- Epsilon `1e-8`.
- `amsgrad=False`.
- `foreach=False`.
- `maximize=False`.
- `capturable=False`.
- `differentiable=False`.
- `fused=False`.
- Global gradient-norm clipping at `1.0` with norm type `2` and
  `error_if_nonfinite=True`.
- Weight decay `0.01` on every trainable matrix, including embeddings and the
  output matrix.
- Weight decay `0.0` on every RMS normalization scale, every route codebook,
  and every retained recurrent `bp`, `ag`, and `og` bias.

Any trainable parameter that cannot be assigned unambiguously to the matrix,
normalization-scale, recurrent-bias, or codebook group is a pretraining
failure. Every optimizer flag and group assignment is duplicated in
`run/prereg.json` and `run/environment.json`.

For an `N`-update stage with `W` warmup updates and peak learning rate `p`, the
learning rate applied to one-indexed update `u` is fixed as:

- `p * u / W` when `u <= W`.
- `p * (0.1 + 0.9 * 0.5 * (1 + cos(pi * (u - W) / (N - W))))` when `u > W`.

The rate is computed before its optimizer update. It reaches `p` at the end of
warmup and `0.1 * p` on the final update. A differential-rate stage applies the
same multiplier to each parameter group's peak rate.

Every cross-entropy loss is unweighted, uses reduction `mean`, and has
`label_smoothing=0.0`. Evaluation calls `model.eval()` and runs inside
`torch.inference_mode()`. Training restores `model.train()` explicitly at each
stage boundary.

## Rung-one intervention semantics

Every routed evaluation condition uses this fixed order inside block `4`:

1. Construct raw route features and the public packed index, then run raw
   public search.
2. Apply the unchanged public one-block forced hook when that condition uses
   it.
3. Apply the query-only effective-route mask.
4. Apply a full-route diagnostic override when the random or source-excluded
   condition uses one.
5. Concatenate the internally supplied local block.
6. Run selected attention.

Raw search telemetry is collected before any intervention. Random and
source-excluded tables never alter the raw route or packed-index calculation.

### Recurrent knockout

At recurrent host blocks `1`, `2`, `3`, `5`, `6`, and `7`, run the complete
mixer on throwaway call-local state, including every reset, update, source
clamp, gate, and finite-state check. Collect its gate and state telemetry,
discard only the returned sequence delta, and expose an exact zero delta to the
host. No throwaway state escapes the call. Host sequence normalization,
residual ownership, feature normalization, and the Transformerov feature block
still run normally.

### Carry reset

In addition to the frozen early-block firewall, set every recurrent layer's
state to exact zero immediately before token `96`. No reset occurs at token
`95` or `97`.

### Carry shuffle

Immediately before token `96`, apply `state.roll(1, dims=0)` to every recurrent
layer state. Batch size is 32, so the cyclic permutation has no fixed point.
The same batch-axis permutation applies to every recurrent layer and head. No
other tensor is shuffled. For causal route scoring, `foreign_condition` is the
batch's condition tensor rolled by one in the same direction, and
`foreign_source` is each current row's own `rule_blocks[foreign_condition]`.
Rows where the rolled condition equals the original condition are reported
separately and are not used for the changed-condition collapse gate.

### Block-4 routed knockout

## Recurrent fidelity, reset order, and state telemetry

Rung one is a reset-amended task protocol, not an unchanged general-recurrence
claim. Its reset-aware implementation must prove all of these boundaries before
training:

- With an empty reset mask, forward outputs at sequence lengths `128` and `512`
  match the frozen chunkwise path with maximum absolute error at most `1e-5`.
- With an empty reset mask, input gradients and every recurrent parameter
  gradient at lengths `128` and `512` match the frozen chunkwise path with
  maximum absolute error at most `1e-4`.
- With the rung-one reset mask, forward outputs, input gradients, and parameter
  gradients match an independently implemented token-sequential reset oracle
  at the same `1e-5` output and `1e-4` gradient tolerances.
- A reset is applied immediately before the named token's state update, never
  after it.
- The source state-norm clamp remains tied to absolute global chunk ends. At
  length `128`, it applies only after positions `31`, `63`, `95`, and `127`.
  At length `512`, it applies after every position `31 + 32 * k` through
  `511`. It never applies merely because a reset-delimited segment ends.
- Rung two dispatches the source chunkwise function unchanged and never enters
  reset-aware code.

The reset-aware token recurrence preserves the frozen source arithmetic. For
each example and head, let `s` be the head state, `q`, `k`, and `v` the current
vectors, and `g` and `beta` the current scalar gates. Compute
`p = k^T s`, then `s_next = g * (s - beta * k outer p) + beta * k outer v`,
then emit `q^T s_next`. A reset replaces `s` with exact zero before this order.
At an absolute global chunk end, emit the token output before clamping, then
compute `n = sqrt(sum(s_next * s_next, dims=(-2,-1), keepdim=True)) + 1e-6`
and carry `s_next * clamp(100.0 / n, max=1.0)`. The norm and clamp are
per-example and per-head in source float32; the epsilon is outside the square
root. No segment boundary, reset, telemetry hook, or output gate changes this
operation order. The position-`96` carry intervention therefore receives the
already clamped state produced at position `95`.

The frozen Transformerov self-check has the stricter per-chunk acceptance
limits `6e-7` at chunk `16`, `7e-7` at chunk `32`, and `1.4e-6` at chunk `64`;
all outputs must remain finite. Direct host parity also covers embeddings,
every block normalization and epsilon, every feature path, recurrent `onorm`,
final `nf`, and the output head. Direct public routing parity covers raw query
and key route features, normalized codebooks, packed-index contents, raw search
IDs and counters, selected attention before masking, and the public internal
route loss.

The primary recurrent gate is exactly `sigmoid(ag(x))`. For each checkpoint,
condition, and recurrent block, concatenate gate scalars in example-index,
head-index, then position-index order, cast the concatenated values to float64,
and perform one population reduction with `unbiased=False`; do not average
batch, head, layer, or per-file means. A block-null aggregate concatenates the
six block vectors in block order `1`, `2`, `3`, `5`, `6`, `7` before the same
single reduction. Record count, mean, population standard deviation, minimum,
maximum, and nonfinite count. Beta/write and output-gate statistics may use the
same axes under separately named statistics but cannot replace the primary
gate.

For every state boundary, detach the state, cast it to float64, and compute one
Frobenius norm per example and head as the square root of the sum of every
matrix element's square. Flatten those norms in example-index then head-index
order and perform one float64 population reduction; never average per-batch or
per-head norms. Record this population separately for every checkpoint,
condition, recurrent block, boundary kind, and absolute position at every
global chunk end and immediately before and after each firewall reset, carry
reset, and carry shuffle.

Intervention-delta telemetry uses final aggregate records, not per-batch rows.
Each record names `model`, `checkpoint_sha256`, `baseline_model`,
`baseline_checkpoint_sha256`, and `baseline_condition` in addition to its

### Crash-atomic JSONL evidence protocol

One shared protocol governs exactly `run/pilot_resources.jsonl`,
`run/resources.jsonl`, `rung1/11/attempts.jsonl`,
`rung1/23/attempts.jsonl`, `rung1/37/attempts.jsonl`,
`rung1/53/attempts.jsonl`, `rung1/71/attempts.jsonl`, and
`rung2/83/attempts.jsonl`. The parent is the sole operating-system writer for
all eight files. Workers send complete `started` or `completed` objects to the
parent and wait for its acknowledgement. The parent sampler follows the same
submission and acknowledgement boundary for complete resource-row objects.
For each exclusive precreation, the parent records the open descriptor's device
and inode as an internal cleanup-consistency check. A preexisting path refuses
exclusive creation. Arbitrary noncooperating replacement or link injection
inside the coordinator private namespace is outside the fault model.

Each file has a parent-owned `last_committed_offset`, initialized to `0` when
the empty file is durably precreated. For one submitted object, the parent
validates the object, encodes exactly one canonical JSON line plus one line-feed
byte, records the prior committed offset, appends the complete bytes, and calls
`os.fsync`. It then reads back exactly the candidate byte range, requires exact
byte and SHA-256 equality, parses it as one line, and revalidates the complete
schema and sequence. Only then does it advance that file's
`last_committed_offset`. After that durable advance and before any
acknowledgement, it checks for a pending handled signal. If one is pending, it
withholds acknowledgement, preserves and charges the newly committed record,
latches `signal_or_interruption`, and then releases deferred signals. If none
is pending, it acknowledges the sender and only then releases deferred signals.
No worker, sampler, logger, or packaging path writes these files directly.

Handled signals are deferred only across the bounded append or rollback
critical section. For any of the first five fault-registry cases, the parent
sends no acknowledgement, calls `os.ftruncate` to the prior
`last_committed_offset`, calls `os.fsync`, and verifies the exact prior
committed prefix before selecting a reason. It then checks pending handled
signals: a pending signal latches `signal_or_interruption` by registry priority;
otherwise it latches `artifact_inconsistency`. It never latches the artifact
reason before durable rollback and the pending-signal check. Only after reason
selection does it release deferred signals. Failure of any truncate, fsync,
seek, read, or file-stat operation in the complete rollback and exact-prefix
proof crosses the unrecoverable-orphan boundary. During abort finalization,
truncation is permitted only for bytes strictly beyond the recorded committed
offset. A committed record is never truncated, rewritten, or fabricated.

Abrupt parent `SIGKILL`, machine power loss, or a storage failure that prevents
required rollback, fsync, `ABORTED.json`, or final checksum writes is outside
the recoverable closure contract. Any staging directory,
filesystem-published-but-not-lifecycle-activated root, or activated run root
left without one complete valid terminal checksum closure is orphaned, is never
a result, is never continued or repaired into a result, and requires a new
absent run root and `run_id`.

Each seed owns one attempt ledger with a zero-based, strictly increasing
`event_sequence`; no run-global attempt counter exists. Immediately after the

The authoritative process set is the parent PID plus the exact single MLX
child PID returned by `Popen`; no process-discovery command is used. For each
sample, the parent forms the sorted comma-separated live PID
string and invokes this exact argv without a shell:

`["/bin/ps", "-o", "pid=,ppid=,rss=,time=", "-p", pid_csv]`

The parser sets `LC_ALL=C`, requires exactly one whitespace-delimited row for
every expected live process, parses PID
and parent PID as decimal integers, and parses RSS as decimal KiB multiplied by
`1024`. It parses `time` as `[[days-]hours:]minutes:seconds[.fraction]`: two
colon-delimited fields mean minutes and seconds, three mean hours, minutes, and
seconds, and an optional integer before `-` means days. It converts the result
with `decimal.Decimal` to integer microseconds using `ROUND_HALF_UP`. A nonzero
exit, duplicate PID, malformed field, unexpected PID, or missing expected live
PID is a hard abort. One typed process-set mismatch may be retried only after
polling process status when the updated expected PID set and the observed PID
set are both proper subsets of the old expected set and the updated set is itself a
subset of the observed set. This permits clean exits discovered after the
`ps` snapshot while rejecting every unexpected PID and every missing still-live
PID, including either condition hidden beside a clean exit. A worker is removed
from the expected live set when its
clean-completion handshake has arrived and its process object reports exit
status `0`; the parent may join it later. A missing PID before that handshake,
or any nonzero or signaled status, is `worker_exit` unless a primary abort is
already latched. On a missing post-handshake PID, the parent polls the process
status before classifying the sample, so an already completed status-`0`
worker is never misclassified while awaiting join.

Swap is sampled with this exact argv without a shell:

`["/usr/sbin/sysctl", "-n", "vm.swapusage"]`

The `C`-locale parser requires exactly one `used = <decimal><unit>` field. It
converts units `K`, `M`, `G`, `T`, or `P` using powers of `1024`, multiplies via
`decimal.Decimal`, and rounds to the nearest byte with `ROUND_HALF_UP`. A
nonzero exit, missing or repeated used field, unknown unit, negative value, or
malformed output is a hard abort. The pilot swap baseline is captured
immediately before pilot worker spawn. The claim swap baseline is captured
immediately after the seven empty claim files are durable following the
`proceed` decision and before any claim payload construction. A second required
swap sample immediately before claim worker
spawn detects construction-time growth; every later claim sample is compared
with the original post-`proceed` baseline. The same argv, parsing, failure, and
five-second sampling contract covers pilot and claim execution.

`run/pilot_resources.jsonl` is the authoritative pilot timeline and
`run/resources.jsonl` is the one authoritative claim-run timeline. Every row
has a monotonically increasing sample ID, phase, active worker, seed, stage and

Per-seed artifacts contain only references to global sample IDs and never copy

## Hard-abort conditions

The following ordered list is the sole exhaustive hard-abort registry and the
same-poll latch priority, from highest to lowest:

1. `signal_or_interruption`
2. `frozen_hash_change`
3. `assertion_failure`
4. `resource_sampler_failure`
5. `nonfinite`
6. `route_overflow`
7. `endpoint_inconsistency`
8. `artifact_inconsistency`
9. `resident_memory`
10. `swap_growth`
11. `claim_elapsed_time`
12. `worker_exit`
13. `unpaired_attempt`

Each numbered registry entry corresponds to the frozen `(reason_code,
condition)` pair in the reviewed payload at
`abort_rules.hard_abort_registry[*]`. Its mandatory non-null descriptive
static `condition` string is copied verbatim from the matching payload entry
whose `reason_code` won. No runtime observation, exception, signal payload,
path, metric, or free-form text may replace or extend that string.

The parent owns one primary abort latch containing that immutable
payload-registry-exact `(reason_code, condition)` pair and monotonic cutoff named
`primary_latch_monotonic_ns`. For candidates observed in the same parent poll,
apply the priority above, then the lower single-child per-seed `event_sequence`.
Once latched, no later or derivative child exit, unpaired
attempt, sampler observation, or packaging failure may replace it.
`unpaired_attempt` can latch only when no earlier primary cause exists.

`signal_or_interruption` covers a received signal or external interruption
while the hard-abort registry is active.
`frozen_hash_change` covers any changed frozen source, configuration, or
preregistration hash after lifecycle activation except the exact governed
`PROJECT_PLAN.md` transition from the reviewed-ready launch digest to the
started training-plan digest. `assertion_failure` covers
any failed registered assertion after lifecycle activation. The same
observations before lifecycle activation are initialization refusals.
After activation, an `InitializationRefusal` is classified as
`artifact_inconsistency`; an underlying unrecoverable orphan bypasses the
registry and terminal finalization.
`resource_sampler_failure` covers an
invalid or failed required `ps` or swap sample. `nonfinite` covers any
nonfinite loss, logit, recurrent state, recurrent gate, gradient, or parameter.
`route_overflow` covers any route-index overflow. `endpoint_inconsistency` and
`artifact_inconsistency` cover their named reload or evidence failures.
`resident_memory` means claim aggregate RSS above `12 GiB` on three valid
samples five seconds apart. `swap_growth` means claim swap use more than
`512 MiB` above its frozen claim baseline. `claim_elapsed_time` means the live
twenty-minute claim deadline is exceeded at any point through successful SHA
packaging. `worker_exit` has the handshake-qualified meaning above.

The failed prepilot-to-pilot and pilot-to-claim transition rollbacks frozen
above are the only pre-latch cleanup exceptions. With signals still deferred,
the first removes an incomplete pilot timeline so the prepilot closure is
reachable; the second removes the incomplete claim surface and proceed pilot
record so the pilot closure is reachable. Each then selects the pending signal
or transition failure by registry priority and latches once. Neither removes a
file retained by its resulting hard-abort closure. Failure to complete either
rollback crosses the unrecoverable storage boundary.

After the primary latch, execute this exact abort finalization order:

1. Stop dispatching new work and preserve the immutable latch.
2. Quiesce or terminate every live worker and join both process objects.
3. Stop the resource sampler after its final valid sample. If and only if the
   primary reason is `resource_sampler_failure`, the retained timeline is
   empty, its writer is still usable, the phase swap baseline exists, and both
   attempted-work counters are zero, attempt one best-effort final sample and
   retain it only when it is valid through the shared parent-writer commit
   protocol. Every other primary reason invokes no sampler during abort
   finalization and preserves an empty timeline as empty. Then stop.
4. Flush and fsync every retained resource timeline and attempt ledger.
5. Validate every retained shared JSONL file through its
   `last_committed_offset`. If bytes exist beyond that offset, truncate only
   that uncommitted suffix with `os.ftruncate`, fsync, and revalidate; never
   alter a committed byte or record. An invalid committed prefix is an
   `artifact_inconsistency` only when detected before the primary latch; a
   validation failure discovered during finalization is derivative and cannot
   replace the latch. Failure to restore and fsync the exact committed prefix
   crosses the unrecoverable storage boundary above.
6. Derive final attempted and completed work, resource state, and last-event
   values from the retained evidence; preserve the primary cause's worker,
   seed, stage, and logical-update identity from the latch.
7. Remove every forbidden partial, performance, completion, summary,
   checkpoint, and pre-abort `SHA256SUMS` file for that phase closure,
   including a provisional stop-decision `run/pilot.json` in a late pilot
   abort. For failed transitions, verify that a partial pilot timeline, or the
   proceed pilot record and every partial claim file and claim-only directory,
   was already removed by the applicable frozen pre-latch rollback.
8. Capture `wall_end_utc`, write and fsync `ABORTED.json` exactly once, then
   generate and fsync `SHA256SUMS` last.

Before any abort cleanup mutation, the runner validates the exact persisted
training-start state, the exact review registry, every relevant cleanup-tree
device and inode identity, and the absence of symbolic paths. Any mismatch is an
unrecoverable orphan and leaves foreign bytes untouched. Failure of required
cleanup, `ABORTED.json` creation, or `SHA256SUMS` creation before the terminal
commit is also an unrecoverable orphan. A provisional `ABORTED.json` is removed
only when its current identity still matches the one latched by this invocation.

`ABORTED.json` is never written before workers and evidence are final. A hard
abort makes no performance claim and always requires a new run root. Writing
`ABORTED.json` does not itself make the closure terminal: the immutable primary
latch remains active while the checksum is packaged. The abort closure becomes
terminal only after its final `SHA256SUMS` fsync; the registry and handled-
signal mutation handlers then deactivate, and no later event may rewrite it.

A performance-gate failure is not on this list. It does not stop the remaining
seeds or suppress a negative result.

## Gradient and codebook claim boundary

The gradient audit enumerates every parameter separately for every model and
stage: donor, router-only, joint, dense base, dense continuation, and rung two.
Each entry has these required fields:

- `model`, `stage`, `name`, `block`, `shape`, and `category`.
- `requires_grad`, `optimizer_member`, `parameter_group`, `peak_lr`, and
  `weight_decay`.
- `grad_none_steps`, `grad_zero_steps`, `grad_nonzero_steps`, and
  `grad_nonfinite_steps`.
- `update_zero_steps`, `update_nonzero_steps`, and `update_nonfinite_steps`.
- `first_nonzero_step`, `start_sha256`, `end_sha256`, `update_l2`,
  `update_max_abs`, and `classification`.

Allowed classifications are `learned_with_evidence`,
`trainable_but_no_gradient`, `frozen_by_design`, `updated_only_by_decay`, and
`nonfinite_failure`. Every block-`0` router value is classified separately as
inactive. Recurrent biases, every normalization scale, embeddings, head,
feature matrices, routed projections, codebooks, and dense-only or
routed-only values remain individually visible.

Static inspection predicts that the discrete public search may leave route
codebooks with `None` or zero gradients. A codebook may be called learned only
if it receives a nonzero gradient and a nonzero update not attributable to
weight decay. Codebooks use zero weight decay, so this distinction is direct.
Otherwise they are serialized route values without an observed learning path.
Query and key projections receive the same explicit classification; no
aggregate router count may hide an inactive parameter.

## Artifact contract

The schema identifier is `todorov.cpu-witness.1`. In this contract,
"published run" without a qualifier means lifecycle-published and activated;
"filesystem-published" names only the bounded durable-final-path state before
activation. One published execution has one final run root; every path below
is relative to that root. Before filesystem publication, the same paths exist
only under the same-filesystem initialization sibling. During the bounded
post-rename window they exist at the final path but are neither a result nor an
activated run. No result artifact is written anywhere else.

Every JSON payload and JSONL row uses UTF-8 canonical JSON with
`sort_keys=True`, separators `(",", ":")`, `ensure_ascii=True`, and

## Result interpretation and kill rule

A positive rung-one result establishes only that the fixed reset-amended
synthetic composition used both recurrent cue carry and routed selected-set
retrieval under the preregistered controls. It does not establish unchanged
general recurrence. A positive rung-two result separately establishes
aggregate tracking on the amended held-count query generator in another
checkpoint with the same host geometry and unchanged chunkwise recurrence. It
does not reproduce Transformerov's published-scale count run. Passing both does
not establish one checkpoint that solves both tasks, natural-language
competence, general world modeling, external carried state, compression,
replay, imagination, sublinear end-to-end cost, or a novel mechanism.

If any rung-one seed or control fails, the combined composition claim is dead
for this preregistration. Publish the complete negative result and localize it
to routing, recurrent cue carry, attention use, optimization, or a baseline
failure from the frozen telemetry. Do not repair it through unregistered seed,
step, schedule, route, or loss changes. If rung two fails, the Transformerov
aggregate-tracking role is not reproduced in this host.

This run card authorizes and defines only the base composition. It neither
defines nor launches the later reciprocal-feature or local training-protocol
stages. After the complete base result, positive or negative, is preserved and
reviewed, [[PROJECT_PLAN]] permits each later candidate only through its own
mechanism contract, reviewed run card, assertions, resource pilot, and matched
isolated controls. A base failure cannot be repaired by activating either
candidate, and final integration may contain only changes that pass their
separate isolated gates.
